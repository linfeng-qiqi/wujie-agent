# 架构设计

## 设计取舍

| 方式 | 优点 | 缺点 | 本项目 |
|---|---|---|---|
| 服务端联网工具（模型自己搜） | 实现简单 | 中间步骤不可见、不可中断、长正文回灌吃 token | 不作主线 |
| 客户端爬虫 + 工具循环 | 每步可控、可播报、可中断、结果可缓存 | 需自己写爬虫 | **主线** |

结论：要「每一步可见」和「随时能停」，必须把工具循环放在客户端。

## 整体流水线

```
QQ 消息（文字/图片/文件）
  → ① 接入层（bus.py：解析消息段，附件落盘校验）
  → ② 聚合层（信号驱动：附件就绪 + 静默 + 结束词）
  → ③ 分流层（控制命令 / 追问直答 / 新任务建 Agent）
  → ④ 调度层（任务队列、状态机、取消标志）
  → ⑤ 协调器（规则化拆解，毫秒级）
  → ⑥ 专职 Agent 群（搜索/文档/记忆，并行 + 逐步播报）
  → ⑦ 结果回收（检查完整性、跑题拦截）
  → ⑧ 整理（去重、排序、排版）
  → ⑨ 发送层（推给 QQ）
  → ⑩ 反馈层（文档保留确认）
  → 存储层（SQLite：任务、消息、附件、事件、记忆、缓存）
```

## 分流：什么时候建 Agent

不是每条消息都建 Agent。分流规则（`agents.py::needs_agent`）：

- **直接回答**（不建 Agent）：寒暄、短追问、常识问答、带上下文的指代（「你这查的是几点的？」）
- **建 Agent**：查询/搜索、写作/生成、多任务、带附件

关键点：短追问优先判定，避免「你这查询的是几点的？」里的「查」字被误判成搜索任务。省略句执行前先做上下文补全（`resolve_query`），「高铁票呢」会接上上一句的航线。

## 协调器：规则化拆解

早期用模型拆解，CPU 上要 40~60 秒且会凭空冒出「查询价格」这类幻觉子任务。现在改为纯规则：

- 零模型调用，实测亚毫秒级
- 用户原话完整保留为任务目标
- 只在明确的分号、换行、「另外/同时/分别」时才拆多任务
- 从源头杜绝幻觉子任务

## Agent 角色

| Agent | 职责 | 模型 |
|---|---|---|
| 协调器 | 理解意图、规则化拆任务 | 无（规则） |
| 搜索 Agent | 多源联网、抓页、整理 | 本地 / flash |
| 文档 Agent | 附件解析、理解 | 本地 / flash |
| 记忆 Agent | 稳定事实召回与写回 | 无（本地规则） |
| 整理 | 汇总、去重、排版 | 本地 / flash |

并发上限默认 4。每个 Agent 独立超时；单个失败不拖垮全局。

## 联网搜索：多轮研究式检索

`crawler.py` 的核心不是「搜一次」，而是「找不到就继续找」：

1. 8 个递进搜索词：原句 → 核心词 → 官方/通知 → `site:gov.cn`/`site:edu.cn` → 年份回退 → 天气定向站
2. 最多 6 轮，每轮 5 源并发（360 / 必应中国 / 搜狗 / 必应国际 / 头条）+ 抓多页 + 评分
3. 没达标就继续换词，还会从已抓标题里提炼新词接着找
4. 每一步写进 Agent 动作轨迹（制定词 → 搜索 → 读页 → 评分 → 换词继续）
5. 只要有素材就一定整理输出，不再因质量闸门没过就丢弃

**分层缓存**：事实 30 天 / 新闻 2 小时 / 天气 30 分钟 / 票务 15 分钟。命中直接返回旧答案，零 token。

## 记忆系统

- `memory_facts`：稳定事实（「我叫…」「我喜欢…」），本地规则抽取，零 token
- `memory_episodes`：情节原文
- `memory_skills`：技能
- `memory_hits`：命中统计

只有稳定事实类才注入新任务上下文；天气/票价等时效内容不写长期记忆，避免用旧数据污染回答。

## 成本与可靠性设计

本地 CPU 模型（如 E5 老平台）推理慢，做了几处硬约束：

- 本地模式失败**不回退到失效的在线密钥**，而是用素材原文兜底
- Agent 等待上限（300 秒）大于「多轮搜索 + 整理」总时长，避免误判后台仍在跑的任务为失败
- 整理素材压到约 900 字，超时给足余量
- 关思考、`keep_alive` 常驻、单并发，避免反复加载模型

## 错误自愈

- 单 Agent 失败按类型重试（语法/参数/空输出/网络），认证失败不重试
- 输出跑题拦截：命中叙事词或与问题零共同字时，丢弃模型输出，改用原始素材
- Synthesizer 不再因个别 Agent 失败就判「全部失败」——有结果就用结果

## 存储

SQLite，WAL 模式（读写互不阻塞，支持任务运行中实时查询）。每线程一个连接，避免锁竞争。事务表包括：任务、消息、附件、事件、Agent 运行、Agent 动作、记忆、缓存、API 用量、文档、追溯原文。
